Measured on 2026-10-02 with `bun run measure packages/api/scripts/production-counts.json`.
The command seeds a local D1 with deterministic synthetic rows matching the
production row counts (`packages/db/src/audits/row-counts.sql`, no personal data)
and reports, per procedure, the D1 statements issued, the rows D1 read (statements
replayed with `.all()` to get `rows_read`), the JSON response size, and real tables
scanned without an index. Run it again with `growth-counts.json` (3× rows) to check
headroom.

## Findings and decisions

- **All public responses are far below the 512 KB budget.** The largest is
  `tvSergipe.list` (38 KB; 114 KB at 3× growth). No public collection needs
  pagination yet.
- **Full scans are on small tables or unavoidable.** `posts` (50 rows), `roles`
  (11), and the admin `tournaments` list scan cheaply. `players.search` reads
  every player because `LIKE '%word%'` cannot use an index; at ~5,500 rows this is
  fine. Revisit with SQLite FTS5 only if search latency becomes visible.
- **Ratings count query is kept.** `players.withFilters` reads ~2,400 rows per
  uncached request, mostly the exact `COUNT(*)` over active players, which the
  pagination UI needs for its page total. Responses are edge-cached for 120 s.
- **Offset pagination is kept.** Page 50 of the ratings reads ~4,450 rows versus
  ~2,500 for page 1; keyset pagination is not worth the complexity at this volume.
- **Lookup-list TTLs stay at 300 s.** `clubs`, `locations`, `titles`, and `roles`
  read 11–182 rows; a longer TTL would save little and lengthen the anonymous
  staleness window (ADR 0003).
- **Indexes match the query shapes.** The rating, `active`+rating, and
  `active`+`birth_date` composites serve the ratings filters and ordering; no index
  was added or removed.
- **Fixed from this baseline:** `titledPlayers.list` now filters with
  `id IN (SELECT player_id FROM players_to_titles)` (6,128 → 1,042 rows read); the
  admin player picker searches instead of loading all players (it truncated at
  5,000 of 5,384); the Swiss Manager export no longer stops at 500 players; the
  admin posts list no longer ships post bodies.

## Guardrails

- Production logs `[trpc] costly procedure` for any procedure taking ≥100 ms or
  issuing ≥8 D1 queries, and `[resource] collection reached its row cap` when a
  list returns exactly `PUBLIC_COLLECTION_LIMIT` rows (`clubs.list` would reach it
  at ~2.7× today's clubs).
- `bun run check:ssr` renders public pages on the same synthetic volume and fails
  when HTML exceeds its per-route budget.
- `e2e/requests.e2e.ts` fails if hydration refetches SSR data, a navigation needs
  more than two API requests, or a public page calls an admin procedure.
