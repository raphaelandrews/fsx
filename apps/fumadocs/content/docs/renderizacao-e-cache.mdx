# Renderização e Cache

Este documento descreve como o site renderiza as páginas e quais camadas de
cache existem, para facilitar mudanças futuras e registrar os prós e contras
de cada alternativa.

## Estratégia atual

- **Páginas com dados** (início, ratings, notícias, comunicados, jogadores,
  campeões, circuitos, TV Sergipe, bullet, membros, links e o painel) são
  renderizadas no servidor **a cada requisição** (SSR no Worker).
- **Páginas estáticas** (`/sobre` e `/normas-tecnicas`) são
  **pré-renderizadas** no build.
- As páginas dinâmicas **não** são pré-renderizadas.

No servidor, o tRPC é chamado **em processo** (sem uma requisição HTTP do
Worker para ele mesmo). No navegador, o tRPC continua usando `/api/trpc`.

## Camadas de cache

- **Cache de borda do tRPC** — respostas `GET` públicas são cacheadas na Cache
  API do Cloudflare, com TTL por procedimento (30–300 s). Requisições
  autenticadas ignoram o cache.
- **React Query (navegador)** — `staleTime` de 5 minutos por padrão e 60
  segundos para publicações (notícias e comunicados).
- **Prefetch de rota** — `defaultPreload: "intent"` pré-carrega o código e os
  dados da rota ao passar o mouse ou focar um link.
- **CDN** — JS, CSS, imagens e fontes são servidos pela camada de assets e
  cacheados pelo Cloudflare.

> A navegação entre páginas (client-side) é praticamente instantânea por causa
> do prefetch e do cache do React Query. A pré-renderização afeta apenas o
> **primeiro carregamento** de um documento (visita inicial, recarregar, digitar
> a URL ou rastreadores).

## Opções

### 1. Pré-renderizar tudo (abordagem anterior)

O build gerava HTML estático para todas as páginas alcançáveis por links
(`crawlLinks: true`) e a camada de assets os servia diretamente.

**Prós**

- TTFB baixíssimo no primeiro carregamento (arquivo estático na CDN).
- Menos leituras no D1 e menos uso de CPU do Worker por visita.
- SEO garantido (HTML completo para rastreadores).

**Contras**

- **Conteúdo congelado no build**: um post novo só apareceria no HTML
  pré-renderizado no próximo deploy (o cliente ainda refazia a busca após a
  hidratação, mas o primeiro paint podia estar desatualizado).
- **HTML vazio/quebrado quando faltava dado no build** — foi o que causou o
  erro React #419 (limites de Suspense não resolvidos).
- Páginas fora do rastreamento (ex.: `/jogadores/<id>`) nunca eram
  pré-renderizadas e dependiam do SSR de qualquer forma.

### 2. SSR a cada requisição

Todas as páginas com dados são renderizadas pelo Worker no momento da
requisição.

**Prós**

- Sempre atualizado, sem deploy.
- Nunca grava HTML desatualizado ou vazio.
- Metadados de SEO gerados por requisição.

**Contras**

- TTFB um pouco maior que um arquivo estático (ainda rápido em Workers).
- Mais leituras no D1 e mais CPU do Worker (escala com o número de
  carregamentos de documento).
- O HTML não é cacheado na borda por padrão — mais requisições à origem.

### 3. Pré-renderizar só páginas estáticas (atual)

Combina o melhor dos dois: SSR para páginas com dados e pré-renderização
apenas para páginas sem dados.

**Prós**

- TTFB instantâneo para as páginas estáticas, sem risco de conteúdo obsoleto.
- Simples e previsível.

**Contras**

- Poucas páginas se qualificam (apenas `/sobre` e `/normas-tecnicas`).

### 4. SSR + cache de HTML na borda (não implementado)

Cachear o HTML das páginas públicas anônimas por um curto período na borda.

**Prós**

- Perfil de custo parecido com o estático: carregamentos repetidos da mesma
  URL não geram Worker nem leituras no D1 durante a janela de cache.
- Ainda atualizado dentro de ~60 s.

**Contras**

- O Cloudflare **não** cacheia respostas de Worker por padrão: exige uma
  **Cache Rule** ("Cache Everything") no painel, além do cabeçalho
  `Cache-Control`.
- Precisa **ignorar o cache quando há cookie de sessão**, para nunca servir a
  visão de um usuário autenticado a visitantes anônimos. O Cloudflare ignora
  `Vary: Cookie`, então isso é feito por regra (bypass por cookie), não só por
  cabeçalhos.
- Se configurado errado, pode servir páginas desatualizadas ou vazar o estado
  autenticado.

## Recomendação

Manter a abordagem atual (SSR para páginas com dados + pré-renderização das
páginas estáticas). O tráfego do site é baixo, as leituras no D1 são baratas e
o Workers não cobra egress; a complexidade do cache de HTML na borda não se
justifica de forma preventiva.

Adote a **opção 4** apenas quando as métricas justificarem (aumento de
requisições ao Worker ou de linhas lidas no D1, por exemplo em dias de
torneio).

## Onde alterar

- **Pré-renderização** — `apps/web/vite.config.ts`:

```ts
tanstackStart({
  pages: [
    { path: "/sobre", prerender: { enabled: true } },
    { path: "/normas-tecnicas", prerender: { enabled: true } },
  ],
  prerender: {
    enabled: true,
    crawlLinks: false,
    autoStaticPathsDiscovery: false,
    failOnError: true,
  },
}),
```

- **Link do tRPC no servidor** — `apps/web/src/router.tsx` usa
  `unstable_localLink` no servidor e `httpBatchLink` no navegador.
- **Cabeçalhos/cache** — `apps/web/src/routes/__root.tsx` (`headers`) e
  `packages/api/src/security-headers.ts`.
- **TTLs do cache de borda do tRPC** — `apps/web/src/routes/api/trpc/$.ts`
  (`PROCEDURE_TTL_SECONDS`).
