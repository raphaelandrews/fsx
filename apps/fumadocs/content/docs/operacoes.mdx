# Operations and Recovery

## Backup

Run `bun run db:backup` from the repository root. The remote backup is written
outside the repository under `~/Backups`, with private permissions, a manifest,
and a checksum when `sha256sum` is available. Backups older than 90 days are
removed after a successful export; set `BACKUP_RETENTION_DAYS` to a value from
1 to 3650 to change the retention window. Do not include backup files in
commits, support tickets, or logs.

## Restoration

Run `bash scripts/verify-d1-backup.sh <backup.sql>` at least quarterly and before
any destructive migration. It imports the SQL into an isolated SQLite database
and checks database and foreign-key integrity. For a full D1 recovery exercise,
restore to a separate staging D1 database, apply compatible migrations, then run
row-count and smoke checks before promoting that database. Never use a recovery
exercise as a direct production overwrite.

## Deploy Smoke Test

Set `BASE_URL` and `MEDIA_SMOKE_URL` to the deployment origin and a known public
media URL, then run `bash scripts/deploy-smoke-test.sh`. The test covers the
login/session endpoint, a public page, a public tRPC query, the unauthenticated
admin guard, and media delivery. Run it after each production deployment.

## Deployment Order

1. Validate code, tests, types, lint, build, and migrations.
2. Apply compatible migrations through Alchemy/D1.
3. Deploy the Worker that consumes the new schema.
4. Run smoke tests for login, a public route, a public tRPC query, the admin
   guard, and media delivery.

Application rollback does not automatically undo a D1 migration. Destructive
migrations require a restoration plan before deployment.

## Monitoring and Media Cleanup

Keep Worker observability enabled and alert on deployment/migration failures,
elevated 5xx responses, and rate-limit spikes. Rate-limit logs contain only the
scope, request ID, and retry window; the scheduled maintenance Worker removes
expired rate-limit rows every fifteen minutes. Never add IP addresses or request
payloads to operational logs.

When deleting or replacing player/post images, use the admin workflow so the
record and R2 object are reconciled. Periodically compare the `players.image_url`
and `posts.image_url` values with keys listed in the `fsx-images` R2 bucket; only
delete objects that are absent from both tables and older than the review window.
Take a backup before bulk cleanup and record the number of objects removed.

For query-plan review, run `packages/db/src/audits/query-plans.sql` against a
production-like D1 clone and record row counts and response sizes with the plan
results. Do not add indexes from a small local seed; compare realistic
cardinality and D1 read/CPU metrics first.
