Routers are in `packages/api/src/routers` and are mounted in
`routers/index.ts`. Access levels:

- **public**: `publicProcedure`, anyone.
- **admin**: `adminProcedure`, the owner only (see [Authentication](/architecture/authentication)).

**Edge TTL** is the edge cache lifetime from `PROCEDURE_CACHE_POLICY`; "—" means
the response is never cached. Mutations are never cached.

## Common errors

Every procedure can return these codes (see [Runtime](/architecture/runtime#errors)):

| Code | When |
| ---- | ---- |
| `BAD_REQUEST` | Zod input validation failed (`data.zodError` lists fields), a check or not-null constraint failed, or a procedure-specific rule was broken. |
| `UNAUTHORIZED` | Admin procedure without a session. |
| `FORBIDDEN` | Admin procedure with a session that is not the owner. |
| `NOT_FOUND` | `byId`, `bySlug`, `forEdit`, `update`, or `delete` matched no row. |
| `CONFLICT` | A unique or foreign-key constraint failed: a duplicate name ("A club with this name already exists."), or a delete blocked by references, whose message names them ("Club “X” cannot be deleted yet: it is still used by 14 players. Reassign them to another record or remove them first."). See [deletion behavior](/architecture/domain-model#deletion-behavior). |
| HTTP `429` | Not a tRPC error: the HTTP handler rejects the request before tRPC runs when the per-IP limit for uncached reads or mutations is exceeded. |
| `INTERNAL_SERVER_ERROR` | Anything else; the message is generic and the details are in the Worker log. |

Every error carries `data.userMessage`: the message of a 4xx rejection, which
procedure code or `normalizeProcedureError` wrote and is safe to show, or `null`
for 5xx and validation errors. The dashboard shows it in error toasts; the
public site shows only its own Portuguese messages.

## Shared input rules

From `packages/api/src/input-schemas.ts`:

| Schema | Rule |
| ------ | ---- |
| `positiveInt` | safe integer ≥ 1 (all IDs) |
| `page` / `limit` | 1–1000, default 1 / 1–100, default 20 |
| `nameText` | trimmed, 1–160 characters |
| `searchText` | trimmed, up to 120 characters |
| `contentText` | up to 500,000 characters (Markdown) |
| `rating` | integer 0–4000 |
| `isoDate` | `YYYY-MM-DD` |
| `httpUrl` | `http` or `https` URL, up to 2,048 characters |
| `imageUrl` | a `players` or `posts` media path (`/api/media/...`, JPEG/PNG/WebP) or an `httpUrl` |
| `emblemUrl(kind)` | a media path of that kind (`clubs` or `locations`, SVG allowed) or an `httpUrl`; used by `logoUrl` and `flagUrl` |
| `optionalHttpUrl` | an `httpUrl` or an empty string |
| `filterArray` | up to 50 strings of 1–80 characters |

Update procedures take `{ id, ...fields }`, where every field is optional and
`nullable` fields accept `null` to clear them. Create, update, and delete return
the affected rows (`.returning()`), except where noted.

### Update requests

| Procedure | Access | Input | Output |
| --------- | ------ | ----- | ------ |
| `playerRequests.submit` | **public mutation** | `{ playerId, birthYear?, clubId?, locationId?, cbxId?, fideId?, photo?: { mime, data }, consent: true, website? }` with at least one data field (a photo alone counts) | `{ received: true }`. Stores a proposal; changes no player. There is no nickname field: only administrators set it. An optional photo (JPEG, PNG, or WebP, 1 KB to 2 MB, checked by signature) is stored under `pending/` in R2 only after the open-request caps pass (and at most 100 photos waiting overall, `TOO_MANY_REQUESTS`), removed again if the insert fails. Photos from several requests of one player wait side by side (an admin picks one); approving one deletes the others' objects. Merging players deletes the photos waiting for the removed record. `BAD_REQUEST` without consent, without a data field, or when the hidden `website` field is filled (bots); `NOT_FOUND` for an unknown player; `CONFLICT` at 3 open requests for that player and `TOO_MANY_REQUESTS` at 300 open requests overall (messages are in Portuguese for the public form). When the deployment has a `TURNSTILE_SECRET_KEY`, a `turnstileToken` that Cloudflare confirms is also required, and a missing, rejected, or unverifiable token is a `BAD_REQUEST` |
| `playerRequests.list` | admin | `{ status? }` | Requests with their player, pending first, at most 500 |
| `playerRequests.byId` | admin | `{ id }` | The request with the player's current values and the proposed club and location names |
| `playerRequests.photo` | admin | `{ id }` | The pending photo as a data URL, or `null` when there is none or it expired. Pending photos are never served by `/api/media` |
| `playerRequests.approve` | admin | `{ id }` | In one batch, applies the proposed fields to the player and marks it `verified`, and closes the request. A pending photo is copied to a public `players/` key first, becomes the player's image (the previous one is deleted), and the `pending/` object is removed; returns `photo: "applied" \| "missing" \| "none"`. A taken CBX/FIDE ID or nickname fails with `CONFLICT` and leaves both untouched (the copied photo is removed); `CONFLICT` if already reviewed |
| `playerRequests.reject` | admin | `{ id, reviewNote? }` | Closes the request and deletes its pending photo; the player is untouched |
| `playerRequests.delete` | admin | `{ id }` | Removes the request with its proposed data and pending photo |
| `playerRequests.deleteReviewed` | admin | `{ olderThanDays? }` (default 90) | `{ deleted }`: removes approved and rejected requests decided longer ago than that, with their proposed data. Pending requests are never deleted |
